## P0 — первая настоящая прошивка STM32F407

Цель: воспроизводимо получить корректный ELF и полученный из него BIN для
заявленного STM32F407VGT6, программно проверенные и готовые к отдельно
разрешённому стендовому запуску через ST-Link. Первый базовый запуск ee7d179 подтверждён22ноября; полные stress/physical
проверки этим не закрыты.

Подтверждённый исходный статус — [отчёт владельца](HARDWARE_STATUS.md):
DevEBox STM32F4VX_M Ver. 2.0; сообщён VGT6; ST-Link V2/SWD работает;
Cortex-M4r0p1; raw ID 0x101f6413; Flash 1024 КиБ; 3,252 В;
дамп 1 048 576 байт, таблица векторов структурно проверена. Нового чтения
устройства или бэкапа для подготовки этого плана не выполняли.

В одном P0 PR выполнить:

1. Изучить официальные datasheet/reference/programming manual и device startup
   ST для STM32F407VGT6. Зафиксировать источники, редакции и проверенные таблицы
   Flash/SRAM/CCM/секторов/IRQ/векторов. Различать документированную карту выбранного
   MCU и фактическую проверку экземпляра. Утвердить linker MEMORY/sections,
   MSP/stack, data/BSS init, vector count/alignment/reserved entries и обработчики.
   Учесть ограничения CCM и доступа DMA; не выводить объём RAM из объёма Flash.
2. Собрать самостоятельный стендовый образ по этой карте, с настоящими
   startup/linker/Reset_Handler и точными версиями toolchain/device sources/
   лицензий. ELF, BIN, map, size, SHA-256 и source commit должны относиться к
   одной сборке. Synthetic probe сохранить как тест; он не заменяет этот образ.
   Профиль не резервирует будущие CAN bootloader/app/staging разделы.
3. Для первого запуска явно использовать HSI. Не включать неподтверждённый HSE
   или предположительные PLL/частоты. Проверить согласованность SystemCoreClock,
   таймера heartbeat и настроек startup; измерение частот на плате — отдельный этап.
4. Обеспечить запрет STEP/DIR, ENABLE, шпинделя и остальных выходов движения
   во всех путях boot/reset/fault/watchdog. Не инициализировать motion GPIO,
   таймерные/DMA выходы и альтернативные функции по предполагаемой распиновке.
   Не угадывать «безопасный» уровень ENABLE. Для первого стенда исполнительные
   устройства отключены; отсутствие записей GPIO не является physical inhibit proof.
5. Добавить ограниченную диагностику без назначения неизвестных пинов:
   состояние запуска, heartbeat, причина reset, fault context в RAM, доступные
   через SWD. Для исполнения не требуются UART, LED, подключённый debug host
   или обязательный semihosting. Диагностика должна позволять проверить, что
   реально работает новый образ, а не только подключается отладчик.
6. Реализовать обработку исключений и явную watchdog policy: безопасный отказ,
   сохранение диагностического контекста, контролируемые reset/recovery пути,
   отсутствие бесконечного обслуживания watchdog из fault handler. Старт и
   обслуживание watchdog, влияние остановки debugger и границы времени описать;
   аппаратное поведение и точность timeout не объявлять проверенными до стенда.
7. Добавить сборку реального профиля и проверки в CI: размеры Flash/SRAM/CCM/
   стека, отсутствие overlap/overflow, entry/SP/Thumb handlers/полная vector table,
   соответствие ELF↔BIN↔map. Добавить содержательные отрицательные проверки
   ошибочных границ/векторов и сохранить прежние необходимые tests/guards.
   В том же PR согласовать scoped instructions и запреты старого synthetic-only
   профиля с явным проверенным bench profile; не отключать проверки общей маской.
8. Подготовить точную процедуру ST-Link установки и восстановления полного
   заводского дампа: проверка идентичности платы/состояния защиты и бэкапа,
   hash/размер/независимая копия, точный образ/коммит, проверка записи и план
   восстановления/диагностики отказа. Процедура сама по себе не разрешает её запуск.
   Не менять option bytes и не выполнять необратимые операции.

Приёмка P0: deployable ELF/BIN, map/size/hash/source/version evidence, успешные
CI/проверки памяти и векторов, описанные HSI/fault/watchdog/no-motion поведение,
SWD diagnostics и ST-Link install/restore runbook. Образ имеет статус
«базовый стенд ee7d179 PASS» с явными пределами из hardware evidence.
Новая сборка не наследует аппаратную проверку только по тому же profile name.

HSE и motion pinout не являются предпосылками сборки HSI/no-motion образа.
Проверка официальной памяти/векторов — часть P0, а не новая цепочка подготовительных
PR. Полная надпись owner, driver sectors/protection и SHA/independent copy/full
snapshot restore теперь подтверждены. Базовые boot/data-BSS/CCM-word/guards/watchdog/fault теперь PASS;
полные RAM/CCM stress, частоты, GPIO/CAN и power-loss recovery ещё нужно проверить. Новый образ
требует нового точного разрешения; предыдущие аппаратные сеансы завершены.

## P1 — полноценный ESP32-S3 OTA

Результат: существующий HMI устанавливает проверенный образ в неактивный слот,
проходит self-test и подтверждает загрузку; неудачный запуск откатывается.
Использовать уже реализованные HTTPS/signature/SHA/compatibility/session APIs,
LVGL owner и bounded workers; не создавать заново verifier или downloader.

- Утвердить расчётом схему 16 МиБ: factory recovery, otadata и два OTA-слота,
  с проверкой размеров реальных образов и запаса. Точные адреса и размеры
  рассматриваются в P1; текущая factory-разметка в этом PR не меняется.
- Подготовить отдельную безопасную USB-миграцию: проверенный полный backup,
  сохранность настроек, проверка bundle/layout, recovery/restore. Разметка
  не мигрирует обычным app OTA; запись только после отдельного разрешения.
- Перед установкой проверять цифровую подпись по локальному доверенному
  публичному ключу, SHA-256, полный размер и hardware/profile compatibility.
  Определить доверенный local context/key provisioning; не выдавать test key
  или версию из git display за production trust.
- Писать только неактивный слот. Потеря Wi-Fi, cancellation, bad signature,
  short/oversize image и потеря питания не уничтожают рабочий/recovery образ.
  Подготовить fault/power-loss проверки download/write/select/first-boot этапов.
- Использовать штатный ESP-IDF rollback, ограниченный self-test после загрузки
  и явное подтверждение исправного приложения. Проверить реальный LCD/LVGL,
  GT911, Wi-Fi/reconnect и доступность recovery; не считать одну компиляцию тестом OTA.
- Измерить SRAM/PSRAM minima/largest blocks и стеки во время HTTPS/verify/write/
  UI/reconnect, длительность операций и откат; не экстраполировать прежнюю HEAD-пробу
  на полный OTA. Сохранить SDK 6.1.1 и проверяемый резерв 5.3.2.

Secure Boot/Flash Encryption/eFuse и прочие необратимые настройки не изменять
без отдельного разрешения. Установка требует exact-image operator approval;
автопроверка обновлений не означает автоустановку.

## P3 — физический CAN

Результат: минимальный подтверждённый обмен ESP32-S3↔STM32F407 на изолированном
стенде после получения трансиверов. Сохранить существующий протокол; новый
драйвер/адаптер/абстракция допустимы только для конкретной аппаратной интеграции.

Проверить схему/ревизии, напряжения, землю, трансиверы, терминаторы, распиновку,
USB/CAN mux и согласованные IDs/bitrate. Проверить ошибки, тайм-ауты, bus-off/
disconnect/reconnect и восстановление без разрешения движения. Получить логи
обоих устройств и реальные измерения. До этого CAN аппаратно не проверен.
Аппаратные операции требуют отдельного разрешения, drive outputs запрещены.

## P4 — STM32 OTA через CAN

Результат: независимый bootloader принимает через ESP32 OTA Manager настоящий
подписанный STM32 образ, проверяет и записывает Flash с восстановлением после
прерывания. Зависимости: реальный профиль/карта памяти P0 и physical CAN P3.

По проверенной секторной геометрии/защите определить bootloader/app/staging/
metadata/recovery размещение и power-loss policy; не резервировать адреса сейчас.
Повторно использовать существующие transport и independent crypto/lease/model
проверки. Проверять Flash write/readback, полный SHA/signature, vectors, bounds
и recovery до boot activation; старый receipt не заменяет свежую проверку bytes.
OTA запрещено при движении, работающем шпинделе или программе. Для установки
нужны свежие physical quiescent/interlock/recovery условия и подтверждение
оператора на точный образ. CAN/ACK не заменяют аппаратную защиту.

## Приёмка и работа Codex

Небольшой PR должен закрывать законченную функцию, даже когда ей нужны несколько
связанных изменений. Новый software layer требует конкретного потребителя и
объяснения, какой результат текущей интеграции он делает возможным. Использовать
существующие tests и API; добавлять проверки рисков изменения, не расширять
бесконечно модель при отсутствующем адаптере или базовой прошивке.

В отчётах разделять software build/проверки, документированную модель MCU,
подтверждённые аппаратные наблюдения и оставшиеся blockers. Для будущих
аппаратных испытаний заранее подготовить конкретные binary/hash/runbook и
условия стенда, затем запросить разрешение. Сборка/CI/PR не разрешают запись,
чтение устройств, reset, движение, необратимые настройки, merge или release.
